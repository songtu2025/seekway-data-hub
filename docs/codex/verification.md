# Codex 验证与完成报告规范

当任务需要制定验证方案、执行检查、判断是否完成或输出完成报告时，必须读取本文件。

## 1. 项目检查声明

每个项目必须在 README 中记录实际可执行的 Windows 和 Linux/CI 检查命令。两端命令可以不同，但必须覆盖相同能力；本规范不规定脚本名称、脚本语言或任务运行器。

检查命令不得在验证过程中安装依赖、修改项目文件或静默跳过必需检查。项目已有统一入口时优先使用；没有统一入口时按 README 逐项执行。

## 2. 结果状态

每项检查只能报告为：

- **通过**：命令实际执行且退出成功。
- **失败**：命令实际执行但未通过。
- **未配置**：受影响模块缺少必需命令或工具，不能标记完成。
- **不适用**：任务不影响该模块，或项目不存在对应能力；必须说明原因。
- **未自动验证**：缺少自动化工具但已进行人工检查；必须说明方法和局限。

## 3. 最低验证能力

任务影响前端时必须覆盖：

- 格式检查。
- ESLint。
- TypeScript 类型检查。
- 自动化测试。
- 生产构建。
- 已安装组件库和图标库的版本兼容性与重复安装检查；项目未安装时记为不适用。

任务影响后端时必须覆盖：

- Ruff 格式和静态检查。
- 项目选定的 Python 类型检查器。
- pytest。
- 存在 Alembic 配置时执行迁移检查。

存在相应配置时还必须覆盖部署配置和禁止提交文件检查；本项目检查 Docker Compose、镜像构建与宿主机 Nginx。缺少必需命令或工具时不得静默跳过。

## 4. 任务专项验证

新增、修改或评审代码时，还必须使用项目已有工具检查：

- 本次涉及文件的职责和规模。
- 函数圈复杂度、认知复杂度、分支数、语句数、嵌套和参数数量。
- 代码重复、死代码和循环依赖。
- 源码和提交记录中的敏感信息；扫描结果不得显示真实命中值。

项目缺少相应工具时，不得擅自增加生产依赖；应进行人工检查，并在完成报告中列为“未自动验证”。人工检查不能伪装成自动化检查通过。

涉及界面时，必须按 `docs/web-ui-standard.md` 的验收清单验证目标视口、页面状态、键盘路径、焦点、对比度、溢出和横向滚动。

## 5. 规范文件专项验证

新增、合并或升级 `AGENTS.md` 及其专项规范时，还必须检查：

1. 项目原有的业务、架构、检查和禁止事项没有因模板接入或精简而丢失。
2. 根规则、嵌套规则、`AGENTS.override.md` 和专项文档的作用域及优先关系明确。
3. 所有索引路径存在，并且每个索引都说明了准确的读取条件；未同步的专项规范没有残留索引。
4. 相同规则只有一个事实来源，不存在互相冲突、已经失效或由工具稳定强制后仍逐条重复的内容。
5. 新项目根 `AGENTS.md` 不超过 100 行；历史项目超过目标时已经说明保留原因和渐进治理方式。
6. 适用的项目规则链未超过 Codex 当前配置的文档大小限制；接近限制时优先减少始终加载内容。
7. 项目 README 已记录公司规范基线版本、接入日期、项目差异和真实检查命令。
8. 在存在不同目录规则时，从具有代表性的工作目录核对 Codex 实际加载的规则来源和顺序。

## 6. 结果真实性与完成报告

完成报告统一为五项，并如实覆盖相关细节：

1. **结果**：需求与验收标准的完成情况。
2. **修改**：文件、主要行为，以及职责、规模和复杂度检查。
3. **验证**：测试、静态检查、构建、代码健康和界面验收结果。
4. **影响**：数据库、认证、权限、配置、依赖、部署和回滚。
5. **遗留问题**：失败、未配置、不适用、未自动验证和已知风险。

不得为了通过检查而删除测试、修改正确的测试预期、关闭检查规则、忽略类型错误、吞掉异常或隐藏失败结果。

只有满足验收标准、未超出范围、必要检查通过、未隐藏未验证内容且未降低代码健康度时，任务才可以标记为完成。“代码已经生成”“代码能够运行”或“理论上可行”不能作为完成依据。
